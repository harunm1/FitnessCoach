## 2. Architecture

**D1, Next.js.** Server Actions suit forms only our app calls; route handlers suit anything outside callers need, such as webhooks and streaming. A separate API is worth it when other clients call it ([dev.to](https://dev.to/myogeshchavan97/nextjs-server-actions-vs-api-routes-dont-build-your-app-until-you-read-this-4kb9)).

**D4, LLM provider.** Groq's free tier needs no card and allows about 1,000 requests a day on its larger models ([eesel](https://eesel.ai/blog/groq-pricing)). Gemini's free tier is Flash-only with reported limits near 20 requests a day, and free-tier prompts can be used to improve Google's products ([agentdeals](https://agentdeals.dev/gemini-api-pricing-changes)). Groq first, Gemini as fallback, no names or photos sent. Checked 30 October against our own keys: Groq's chat models are now OpenAI's open-weight gpt-oss-120b and gpt-oss-20b and Qwen's qwen3.8-27b, and it no longer serves Llama, so the Llama 3.1 70B result cited in #22 does not carry over directly. Gemini's free key lists the 2.5, 3 and 3.5 Flash models. Both providers ran on the same test profiles (#19). Decided 30 October (#7, eval in COACH_EVAL.md).

**Auth.** Better Auth has a Prisma adapter and a Next.js handler; Prisma's own guide only guards pages in the browser, so we check the session and tier on the server ([Prisma](https://prisma.io/docs/guides/betterauth-nextjs)).

**Auth, the alternatives (checked 30 October).** Auth0 is a managed service: the user store sits on Auth0's side and the free tier ends at 7,500 monthly active users, after which it bills per user ([pkgpulse](https://www.pkgpulse.com/guides/lucia-auth-v3-vs-better-auth-vs-stack-auth-self-hosted-2026)); Auth.js (NextAuth) is the older self-hosted library and defaults to JWT sessions, which cannot be revoked before expiry without a server-side blocklist ([nexty.dev](https://nexty.dev/blogs/nextjs-boilerplate-better-auth-drizzle)); Better Auth is self-hosted, TypeScript-native, keeps users and sessions in our PostgreSQL through a Prisma adapter, and ships rate limiting and CSRF protection ([Better Stack](https://betterstack.com/community/guides/scaling-nodejs/better-auth-vs-nextauth-authjs-vs-autho/), [OpenReplay](https://blog.openreplay.com/betterauth-explained-rapid-developer-adoption/)). Our tiers come from Stripe and must sit next to the user row, so the user store has to be ours; that, and database sessions we can end on the server, is why Better Auth over Auth0, not only that the course recommends it.

**D2, indexes (checked 8 November 2026 and again 10 November, Prisma 7.10.1, PostgreSQL 16).** A foreign key does not create an index on the referencing columns in PostgreSQL: "the declaration of a foreign key constraint does not automatically create an index on the referencing columns" ([PostgreSQL 16, Constraints](https://www.postgresql.org/docs/16/ddl-constraints.html)). Prisma Migrate adds none either (observed in `prisma/migrations`: indexes exist only for `@unique`, `@@unique` and `@@index`), so each index is declared with `@@index` in the schema; on PostgreSQL the default access method is B-tree ([Prisma ORM v7, Indexes](https://www.prisma.io/docs/orm/v7/prisma-schema/data-model/indexes)). Column order matters: equality constraints on the leading columns, plus an inequality on the first column without one, limit the part of a multicolumn B-tree that is scanned; constraints on later columns are only checked inside the index ([PostgreSQL 16, Multicolumn Indexes](https://www.postgresql.org/docs/16/indexes-multicolumn.html)). In our query plans (#78), Postgres did not treat `finishedAt IS NULL` as an equality for ordering, so a `startedAt` column after it left the same sort on the few matched rows: the `Workout` index stops at `finishedAt`. `Plan`'s `active = true` is an equality, so its index also serves the `createdAt` sort. `prisma migrate dev` generates a migration from the schema change and applies it locally; `prisma migrate deploy` applies committed migrations, and our CI runs it on an empty database (`npm run db:migrate:test`) ([Prisma ORM v7, Development and production](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/development-and-production)). We index only what a query on `main` filters or sorts by (#76).

**D2, constraints (checked 10 November 2026, Prisma 7.10.1, PostgreSQL 16).** Two rules are held by the database, not only by the code: one active plan per user, and one open workout per plan. Both are written as read, check, then write (deactivate the old plan, then insert; look for an open workout, else insert), and under PostgreSQL's default Read Committed our 10 November schema audit (#76) reproduced both breaking: a quiz save racing a coach save left two active plans, because each path serialises on a different row lock, and two taps on Start left two open workouts. A constraint holds for every writer and at any isolation level. It beat one shared lock for both writers, which every future writer would have to remember, and `SERIALIZABLE`, which needs a retry loop around every writer. Prisma 7 declares a partial unique index with `where` on `@@unique`, behind the `partialIndexes` Preview feature ([Prisma ORM v7, Indexes](https://www.prisma.io/docs/orm/v7/prisma-schema/data-model/indexes)): `Plan @@unique([userId], where: { active: true })` and `Workout @@unique([planId], where: { finishedAt: null })`. Prisma then offers `Plan.userId` and `Workout.planId` as unique keys in the client although each is unique only among active plans or open workouts, so they must never be used in `findUnique`, `update`, `upsert` or `delete`; the code finds those rows with `findFirst` and the same filter. The workout rule is per plan, not per user: a plan switch does not close the old plan's open workout, and a per-user index would stop Start working after a switch. Closing that workout on a plan switch is not part of this change. A data migration runs first and keeps only the newest active plan per user and the newest open workout per plan, so the index build cannot fail on old duplicates: an older duplicate with nothing logged is deleted, one with sets, a run, a distance, a time or notes is closed at its start time (tested in `tests/integration/migration-dedupe.test.ts`). The race has two orders, both reproduced in `tests/integration/schema-constraints.test.ts`. When the coach save runs first, the quiz save's UPDATE waits on the old plan, then misses the coach's new plan and inserts a second active one; with the index, the quiz save fails with a unique violation instead, which the quiz page's owner handles (tracked in #76). `saveWeek` never meets that violation, because every Plan insert needs a key-share lock on the User row it holds. When the quiz save runs first and holds the old plan, the two saves deadlock and Postgres aborts one of them (Prisma code P2034); which one "should not be relied upon" ([PostgreSQL 16, Explicit Locking](https://www.postgresql.org/docs/16/explicit-locking.html)). If it is `saveWeek`, it retries once, so the newer save wins, as it already does when two coach saves meet at the User row lock; if it is the quiz save, the coach's plan stands and the quiz save fails. Both outcomes are tested. Range checks are CHECK constraints in a hand-written migration, because CHECK is "Not yet" in the Prisma schema and in Prisma Migrate ([Prisma ORM v7, Database features](https://www.prisma.io/docs/orm/v7/reference/database-features)). They are sanity bounds (for example, counts of at least one, RPE 1 to 10, a day index of 0 to 6, 1 to 7 days a week); the coaching ranges stay in `src/lib/coach/schema.ts`. A plain `ADD CONSTRAINT` validates every row at once, which is instant on our demo data; on large tables, `NOT VALID` and then `VALIDATE` in a separate migration would shorten the lock. `Workout.planId` and `Workout.planDayId` get plain indexes, so deleting a plan or a plan day finds the workouts to set to null without scanning `Workout` (#76).

## Exercise data

[free-exercise-db](https://github.com/yuhonas/free-exercise-db): 800+ exercises as JSON with primary and secondary muscles, equipment, level, step-by-step instructions and images, under the Unlicense (public domain). It can seed the exercise library directly and drive the body map from its muscle names.

Hevy's API needs a Hevy Pro subscription and a personal API key tied to one account, so it suits syncing one user's own workouts, not supplying our app's exercise data ([Serval docs](https://docs.serval.com/sections/integrations/hevy)).

### ExerciseBank and four competitors: media, joint data and running (checked 11 Nov 2026; for #8, #92, #94)

**What ExerciseBank holds.** 1,492 exercises filmed in one studio, each with muscles, equipment, movement pattern, difficulty 1 to 5, the joints it loads (nine values: ankle, cervical spine, elbow, hip, knee, lumbar spine, shoulder, thoracic spine, wrist), impact (low, moderate, high), ranked substitutes with a stated reason, and English and French cues ([API docs](https://exercisebank.net/docs)). Plans are priced by monthly end users, not by call: Sandbox is free (25 end users, 5,000 requests a month, video for 50 exercises); Starter is US$29 a month (500 users, all video); Pro $79; Business $199. Solo, US$39 a year, is for one person and "not for an app's users" ([pricing](https://exercisebank.net/pricing), [Solo](https://exercisebank.net/solo)).

**Licence** ([plain-words licence](https://exercisebank.net/license), updated 10 Sep 2026). Allowed: show exercises, clips, descriptions and cues to the product's own users inside the product; store the catalogue metadata and reword or extend it. Not allowed: re-hosting or redistributing video or stills, sharing the key with another product, training machine-learning models on the library without a written agreement, and running "a product available to the public on the sandbox plan". When a plan ends, stored media must be deleted and stored metadata may be kept but not used in a product. Video comes only as signed links that expire (15 minutes by default) and must not be stored (brief caching on the device for playback is allowed); the key must stay on the server ([docs](https://exercisebank.net/docs)). So the free tier is for building and demoing; a public deployment needs Starter. The pricing page invites students to describe their project on its help page; nobody has asked yet whether a course demo qualifies.

**Fit with our 30 cue exercises (PR #102).** Searching nine of the staples by name found a close match for bench press, Romanian deadlift, dumbbell lunge, shoulder press, push-up, pull-up and glute bridge or hip thrust; a plain back squat appears only as variants. Of the 36 results read, two sit in the 50-exercise free-video sample (single-leg Romanian deadlift, dumbbell row to curl) and none is a staple, so the free tier would not show video for the exercises the starter plan uses most. Some records look noisy: "Pull-up" is tagged with barbell equipment and a horizontal pull, and two entries are both named "Rowing" with identical tags (a sample of nine searches, not an audit).

**Running.** A search for "run" returns 73 hits, but they are mostly drills and substring matches. Of the first 50, 26 concern running or sprinting (jog, incline treadmill jog, bounding, high-knees drill, carioca, hurdle run-throughs, sprinter arms) and the other 24 are unrelated core exercises that match the search some other way (crunches, hip lifts, machine abs); the last 23 were read afterwards and none concerns running. These are conditioning drills, not training plans, and video for them is Solo or paid except three (alternating fast feet, single-leg swing hop, split-stance sprinter arms). In our app runs are `PlanRun` rows built by rule (D8), and #8 leaves running form out, so there is nothing for this data to fill.

None of the four pages offers its library for reuse (Hevy has a separate Pro API for one user's own workouts, above), and each reads as a curated library. The routes open to a small team are open data (free-exercise-db, Unlicense, already seeded) or a paid licence (ExerciseBank above; ExRx also sells its exercise database and video as an app licence, [ExRx licensing](https://exrx.net/Store/Other/Licensing)). The cue sources for #102 are ExRx pages; the cues must be in the team's own words, which this note did not check.

**Decision (free only).**

1. Do not put ExerciseBank data or video in the app. Free covers building, not a public deployment, and the public tier is US$29 a month. The library stays free-exercise-db plus the team's own cues.
2. Take the idea, not the data. #94 and #92 need to know which joints an exercise loads. Add `loadedJoints` (the same nine anatomical joint names) and `impact` for the 30 cue exercises, filled in by the team from anatomy references and checked by a second person. Do not copy ExerciseBank's per-exercise values: the metadata is ExerciseBank's property, the licence ties its use in a public product to an active paid plan, and stored metadata may not be used in a product once a plan ends. This is a schema change (foundation) plus 30 rows of data (library), a separate issue after the 15 November core path, not part of #102.
3. Running: no ExerciseBank use. Run days stay `PlanRun` rows built by rule. If run days need a warm-up, a few lines of text in the run builder are enough.
4. Optional, not done: ask ExerciseBank on its help page whether a course demo qualifies for the free tier; only an account holder can send it.

**Limits.** Vendor pages are vendor claims; the competitor pages were read for what they say, not tested in the apps. The ExerciseBank data was read through a free account's search, not through an API key, and nothing was stored. Coverage of the 30 is a name search on nine exercises, not a full mapping.

## Photo storage

Progress photos go in a private Cloudflare R2 bucket, as Farnaz proposed in #16, S3-compatible, with only the object key in the database (D3 in `ARCHITECTURE.md`). The R2 free tier covers 10 GB-month of Standard storage, 1 million Class A and 10 million Class B operations a month, and no egress fees ([Cloudflare R2 pricing](https://developers.cloudflare.com/r2/pricing/), checked 6 Nov 2026). DigitalOcean Spaces, the first choice, has no free tier: $5 a month from the start ([Spaces pricing](https://docs.digitalocean.com/products/spaces/details/pricing/), checked 6 Nov 2026). Enabling R2 goes through a checkout step ([R2 get started](https://developers.cloudflare.com/r2/get-started/), checked 6 Nov 2026); Farnaz reports it may ask for a payment method (#16). Photos build against a local folder first, so the feature does not wait on the account.
