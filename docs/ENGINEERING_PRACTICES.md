# Engineering practices: proposals for discussion

Proposed for the next team meeting, not agreed, except where a point says the [8 November design review](design-reviews/2026-11-08-review.md) decided it. Each one is chosen for how FitnessCoach is built: Next.js, Prisma, and an LLM coach behind a verifier. Whatever the team agrees goes into the README's "How we work". The papers behind these choices have one note each in [docs/papers](papers/README.md).

1. **Small commits every week.** A few small commits a week per person rather than one large push before a checkpoint. The course reads contribution from the Git history, and problems with environment variables or Prisma migrations on the hosted database show up the week they are introduced.

2. **Core path first.** Sign-in, quiz, plan and a logged workout working end to end by the 15 November checkpoint, before photos, Stripe or Redux. Those stay planned in [PLAN.md](PLAN.md) but are not built in parallel with the core.

3. **One schema per boundary.** A Zod schema for every Server Action input, route handler body and the coach's plan JSON; Prisma types for what is stored. The coach is asked for structured output against the same plan schema, so a malformed reply is rejected before it reaches the verifier, the UI or the database.

4. **Three layers of tests, each owner testing their own slice** (decided 8 November, decision 4). Unit tests for pure logic run offline and give the same result every time. Coach logic stays in plain functions, as `generatePlan` and `verify` already are. Tests use saved model replies instead of calling Groq or Gemini, so CI needs no key and costs nothing. API mocking at the provider boundary tests bad replies on purpose: invalid JSON, an unknown exercise ID, an empty plan, a timeout, a rate limit. Integration tests run Server Actions against a real PostgreSQL in CI (#79). A deliberately failing check must fail the CI run.

5. **Model calls only through `src/lib/coach/providers.ts`, and every one is bounded** (the first half decided 8 November, decision 1). No route handler, Server Action or component calls a provider directly, so every model call gets the same limits. A time limit and one retry, then the rule-based default plan. User text sent to the coach is length-capped and marked in the prompt as data, not instructions; off-topic or unsafe requests get a fixed reply, and the verifier checks the result either way. Nutrition is out of scope (decided 8 November, decision 5): diet, calorie, supplement and meal questions get the out-of-scope reply that points to a registered dietitian.

6. **A logger from the start, with no personal data in it.** One module in `src/lib` that logs each coach step (prompt version, model, tokens, time, verifier result) under a request ID. Names, photos and health details never go into logs, prompts or Git; secrets stay in `.env`.

7. **Decisions logged the day they are made.** A row in the decisions table in [ARCHITECTURE.md](ARCHITECTURE.md) with the reason, so the proposal and final report quote it rather than reconstruct it.

## Forms and file storage (Lecture 9, 15 November)

Added 15 November from ECE1724 Lecture 9 ("React Ecosystem and Modern Frameworks", `lecture-9.pdf`). Slide numbers are the ones printed on the slides. The last column says how `main` (9e6f8ef) meets each row; open pull requests are reviewed against the same rows.

| #   | Practice                                                                                                                                                                                                                                       | Slides           | On `main`                                                                                                                                                                                                                               |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 8   | **Core form submission works without client JavaScript.** Pass the Server Action to `<form action={...}>`; an `onSubmit` handler may add checks but must not be the only way to submit. A function passed straight to `action` returns `void`. | 7-8, 10-12       | Quiz, set log, run metrics, coach, trial, photo upload and photo delete use `action`. Sign-in, sign-up and change password use `onSubmit` with the Better Auth client; slide 15 accepts both approaches, so this is noted, not changed. |
| 9   | **Pending state from `useFormStatus` or the `isPending` value of `useActionState`**, not a hand-kept `submitting` flag. `useFormStatus` is called from a Client Component inside the form.                                                     | 17-19, 22        | Every Server Action form takes its pending state from `useActionState`.                                                                                                                                                                 |
| 10  | **Server-returned feedback through `useActionState`**, which can show the result before hydration completes.                                                                                                                                   | 22-23, 27-28, 40 | Every Server Action form listed in row 8.                                                                                                                                                                                               |
| 11  | **A success flag separate from the message.** Code branches on `success` or `status`, never on the message text, so rewording a message cannot break navigation.                                                                               | 34-37            | Action states carry a `status` (`PhotoActionState`, `CoachActionState`, quiz and log states); no client code compares message text.                                                                                                     |
| 12  | **Where code runs.** Client Components for browser interactivity and hooks; Server Components to render and read data; Server Actions for mutations; Route Handlers only for HTTP endpoints.                                                   | 45               | Mutations are Server Actions; the Route Handlers are the Better Auth and Stripe endpoints.                                                                                                                                              |
| 13  | **Files in object storage, metadata in PostgreSQL.** The bytes go to the bucket; a row holds the object key and the owner's user ID, plus whatever the app queries on.                                                                         | 48, 103-105      | `ProgressPhoto` holds `storageKey` and `userId`. Original filename and type are left out on purpose: every photo is re-encoded to WebP, so the type is fixed, and a filename can carry personal data (practice 6).                      |
| 14  | **One module holds the S3-compatible client**, so changing provider (DigitalOcean Spaces or Cloudflare R2) is configuration plus that module. S3-compatible is not identical: ACLs, public access and URL formats differ.                      | 59, 92, 101-102  | `src/lib/storage/index.ts` hands out a `PhotoStorage`; only `src/lib/storage/r2.ts` imports the AWS SDK.                                                                                                                                |
| 15  | **R2 has no object ACLs.** Objects are private by default; public access is a bucket setting (the r2.dev development URL or a custom domain), and `ACL: "public-read"` is not supported.                                                       | 54, 90-91, 96    | Bucket private; photos are shown through short-lived signed URLs (#109).                                                                                                                                                                |
| 16  | **Validate type and size on the server**, even when the browser checks first.                                                                                                                                                                  | 72               | `processPhoto` checks the byte size and reads the real format with sharp (JPEG, PNG or WebP) instead of trusting `file.type`; the Server Action body limit is 4.5 MB (`next.config.ts`).                                                |
| 17  | **Random object keys** (`randomUUID()`), so keys neither clash nor can be guessed.                                                                                                                                                             | 73               | `progress/<userId>/<uuid>.webp`.                                                                                                                                                                                                        |
| 18  | **Secrets never carry the `NEXT_PUBLIC_` prefix**, which ships the value to the browser.                                                                                                                                                       | 93               | No `NEXT_PUBLIC_` variable in `src/` or `.env.example`.                                                                                                                                                                                 |
| 19  | **`<a href={url} target="_blank" rel="noopener noreferrer">` for files and external URLs; `<Link>` for routes inside the app.**                                                                                                                | 83-85            | Internal routes use `<Link>`; photos are shown inline with `<img>`, and `main` has no link to a file.                                                                                                                                   |

## Authentication and authorization (Lecture 10, 20 November)

Added 20 November from ECE1724 Lecture 10 (`lecture-10.pdf`, read in full). Slide numbers are the ones printed on the slides; the last column is checked against `main` (e31e494).

| #   | Practice                                                                                                                                                                                                      | Slides    | On `main`                                                                                                                                                  |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 20  | **Use an established auth library**, not hand-rolled password hashing, recovery or sessions.                                                                                                                  | 7, 11     | Better Auth in `src/lib/auth.ts`, mounted once at `src/app/api/auth/[...all]/route.ts`.                                                                    |
| 21  | **Authentication is not authorization.** Knowing who the user is does not decide what they may do.                                                                                                            | 6, 54, 64 | Tier, trial and plan limits are checked on the server in `src/lib/auth/access-policy.ts`, `tier.ts` and `plan-rate-limit.ts`.                              |
| 22  | **Protected pages check the session in a Server Component and redirect** when there is none.                                                                                                                  | 40-41     | `requireUser` (`src/lib/auth/session.ts`) redirects to `/sign-in`; account, coach, session, onboarding and progress photos call it or `requireAccount`.    |
| 23  | **Ownership is enforced in the query, with the user ID from the server session.** Never trust a user ID sent by the client.                                                                                   | 55, 61    | No Server Action or Route Handler reads `userId` from form data or the query string (checked 20 November); photo keys are `progress/<userId>/<uuid>.webp`. |
| 24  | **`import "server-only"`** on every module that reads the session or the database, so importing it from a Client Component fails the build.                                                                   | 56        | 20 modules import it, including `session.ts`.                                                                                                              |
| 25  | **Session data: props for display, `useSession()` when the UI must react to sign-in or sign-out.** Props are a snapshot; `useSession()` is reactive but adds a request.                                       | 50-53     | Reviewed per PR against this row.                                                                                                                          |
| 26  | **`router.refresh()` after sign-in, sign-out or a client-side mutation** so Server Components re-render with the new state.                                                                                   | 37        | `auth-form.tsx`, `change-password-dialog.tsx`, `billing-controls.tsx`.                                                                                     |
| 27  | **`BETTER_AUTH_SECRET` is random (`openssl rand -base64 32`) and `BETTER_AUTH_URL` is set per environment.** Neither goes in Git.                                                                             | 19        | `.env` only; production values set on the host.                                                                                                            |
| 28  | **Engineering judgment with AI.** Make the design decisions first, break the work into slices that can be verified alone, then check correctness, security, design and maintainability with tests and review. | 72-81     | One issue per slice, owner tests per slice (practice 4), every code PR reviewed by a teammate.                                                             |

## Lessons from Assignment 4 (20 November)

| #   | Practice                                                                                                                                                                                                                              | Why                                                                                       |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 29  | **Exact strings and test IDs from the spec are a contract.** The autograder tests only what the handout states, and tests every stated string.                                                                                        | A4 passed all 11 sample tests by matching every message, class and `data-testid` exactly. |
| 30  | **A failed query renders an error state in place**, from a try/catch in the data function, inside the Suspense boundary.                                                                                                              | The home page stays usable and the failure is visible and testable.                       |
| 31  | **Develop from the Linux filesystem under WSL, or restart the dev server after edits.** On `/mnt/c`, Turbopack misses file changes; `--webpack` sees them but drops Tailwind, which this setup loads only through the Turbopack rule. | Cost an hour on A4's file-edit test.                                                      |
| 32  | **Verify the package before submitting**: run the course's checker, and keep `.env`, `node_modules`, build output and migrations out of the archive.                                                                                  | A4's checker rejected `prisma/migrations/` on the first try.                              |
