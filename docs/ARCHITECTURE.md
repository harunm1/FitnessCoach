# Architecture (draft)

## How it is used

A mobile-first website, used on the phone at the gym and on a laptop at home.

| When   | What the user does                                                                                                |
| ------ | ----------------------------------------------------------------------------------------------------------------- |
| Before | Takes the quiz (goal, days a week, equipment, injuries), gets a plan built from our exercise library              |
| During | Opens today's session: logs sets with large buttons, rest timer, asks the coach ("bench is taken, what instead?") |
| After  | Sees streaks, a calendar heatmap and progress photos                                                              |

The coach is a chat panel on every page, not only the body map. Tapping a muscle on the body map opens the chat with that exercise and spot already filled in.

```mermaid
flowchart LR
  U[Phone or laptop] --> N[Next.js app]
  N -->|Server Actions| DB[(PostgreSQL via Prisma)]
  N -->|signed URLs| S[(Cloudflare R2: private photos)]
  N -->|route handler, streamed| C[Coach]
  C -->|providers.ts only| L[LLM APIs: Groq, Gemini]

  V --> DB
```

## The coach

**Grounded, not free-form.** Every request sends the model this user's profile, plan, last workouts, the current conversation and the matching exercise library entries. The model is stateless; the conversation lives in our database, scoped to the user, so one user's data never reaches another user's request.

**Plans are picked, not invented.** The model chooses exercises by ID from our library and fills sets, reps, rest and a target RPE of 6 to 9 (D17). It cannot name an exercise we do not have.

**A verifier checks everything before it is saved or shown.** Plain TypeScript, unit-tested, no second model:

- the reply matches the JSON schema
- every exercise ID exists and fits the user's equipment and reported injuries
- sets, reps, rest and RPE are in range; no exercise twice on one day
- a swap suggestion targets the same muscle as the original

A plan that fails is regenerated once with the problems listed, then the user gets a rule-based default plan. A rate limit or outage at the provider is retried with backoff, then the request moves to the other provider (D6); only after both fail does the user see the default plan.

**The coach sees the whole library.** Every exercise the user can do (their equipment, nothing that works a reported injury) goes into the prompt by name, grouped by muscle; nothing is cut for length (D7). The model answers with names, code maps them to ids, and the verifier checks the ids.

**Safety rules are code, not prompt.** If the user reports pain (not effort), the coach stops the exercise and suggests a professional. It does not diagnose. The rules are in `src/lib/coach/guardrails.ts` (#43): each user message is to be checked before a model call and each reply before it is shown, once the chat code (#53) and the coach route (#11) call them; a crisis message gets a fixed reply with 9-8-8 and 911, exaggeration in training talk or distress with no training context a short check-in that still names 9-8-8, a model safety check runs first and can only raise the response (D15), a red-flag symptom (chest pain, fainting, trouble breathing) a fixed stop-and-seek-care reply, and disordered eating the NEDIC helpline; a reply that diagnoses or names a dose is replaced; off-topic requests get a one-line redirect; user text only ever goes in as the user message.

**Form feedback questions are bounded:** where it is felt, at which point in the rep, the weight against usual. The answers pick a fix from the exercise's library entry (cues, common mistakes), so the advice traces to text we wrote.

**AI only through `providers.ts`.** `src/lib/coach/providers.ts` is the one module that calls a model API (Groq first, Gemini as fallback, D4 and D6). No route handler, Server Action or component calls a provider directly. A new model path, such as the chat screen (#63) or the exercise chat (#70), goes through it and so gets the retries, timeouts, fallback and `coachLog` record. Coach modules pass typed data to each other, never raw model text. On `main` on 10 November, `providers.ts` and, by the exception recorded under D15, `safetyModel.ts` (the safety check, not yet called on `main`) hold the provider URLs. Core features (sign-in, quiz, rule-based plan, logging) work with no model key (8 November [design review](design-reviews/2026-11-08-review.md), decision 1, #76).

**No nutrition advice.** Scope is lifting, strength training and running. The coach gives no diet, calorie, supplement or meal advice; a nutrition question gets a short out-of-scope reply pointing to a registered dietitian (decision 5, #43).

**Text, not voice.** Voice adds speech-to-text, text-to-speech, microphone permissions and latency, and is not one of the course's advanced features. Streamed text replies are.

D15 changes after the blind review of 10 November (#43):

- **The model call bypasses `providers.ts`, by exception.** Practice 5 sends model calls through `providers.ts`. The safety check is a different model with no fallback provider and its own 3-second limit, and it runs before, and apart from, the coach's provider chain. It is bounded in the same spirit: one attempt with no retry, at most the first 4,000 characters of the normalized text, and the word list reads the whole message.
- **A failed model reading is reported, not hidden.** `screenUserMessageWithReading` returns the model's category, `UNAVAILABLE` when it failed, timed out or gave an unknown label, or `NOT_CONFIGURED`. The caller is to log `UNAVAILABLE` once the chat route (#53, #11) wires the screen in. Labels are read case-insensitively, and an empty API key is refused when the classifier is built.
- **Check-in scope.** "A burden to everyone" and "can't do this anymore" get the check-in even next to a training word. Distress wording keeps the check-in, which names 9-8-8, even beside a pain report or an eating disclosure. Session-tied exaggeration ("I'm gonna die on this run") gives way to the pain or eating reply. Leetspeak and look-alike letters are still left to the model.

D9 in practice (10 November, #85). The quiz asks for training mode (strength, running, both; strength when unanswered). Running and both go through `buildHybridWeek`, the strength and running verifiers, and `saveWeek`, which saves the profile and the plan in one transaction. The quiz does not ask about activity, mileage or pace, so a quiz runner is a new runner: light group, 10 km in the first week, easy pace by feel. This beat asking three more questions in the quiz, which is Mohammad's screen, and reading the stored `Profile.activityLevel`, which no screen sets yet; either replaces the default when it exists. Injury text filters strength exercises only, not run days.
D12 in practice (10 November, #59; corrected the same day after an independent review). Demo mode is one setting, `COACH_DEMO_MODE=1`, turned on for the demo only, with `GEMINI_MODEL` set to Gemini 3.5 Flash-Lite, the fallback model of D6.

- **Fail fast.** In demo mode each provider call stops after 8 seconds instead of 30, including a reply whose body stalls after the headers, and nothing waits for a retry: a rate limit, a server error or a dropped network goes straight to the other provider. In the 30 October round-2 files on the full library, Groq's slowest plan took 3.5 seconds and Flash-Lite's 6.9, both under the limit; the default Gemini Flash took a median of 9.9 seconds in round 1 and would time out ([eval](COACH_EVAL.md)). There is one attempt: a failure of any kind, a provider error, a reply that is not JSON or a plan the verifier rejects, goes to the cache, since a cached plan has already passed the verifier and a regeneration costs another wait. Worst case, both providers stalling, is 16 seconds; a rate limit or no network falls back at once.
- **What comes from the cache.** Coach plans: the real replies from the 30 October eval run (`eval/results/2026-10-30-chain-round2.jsonl`, prompt `plan-v2`), kept in `src/lib/coach/demoPlans.json` with their prompt version and a hash of the plan prompt. When the coach fails, the user gets the first cached plan that passes the verifier for their own equipment, avoided muscles and days; only when none fits do they get the rule-based plan. A test fails when the plan prompt's version or wording changes and the cache does not, so a prompt change forces a refresh (D12's cost). Cached chat replies are the next slice.
- **How the screen says so.** The result is marked `cached`, and the per-call log records the outcome `cached` with the profile whose plan was served. No screen asks the coach for a plan yet: the "Personalize with the coach" action (#58) is to pass the cache in demo mode, save the plan as a coach plan (a model wrote it and the verifier passed it), and say "The coach is busy right now, so here is a plan it wrote earlier for a profile like yours", never that it was just written.
- **The option it beat.** A cache filled from live replies (Vercel's runtime cache, or Next.js `use cache: remote`) is empty until a live call has succeeded, is kept per region and per environment, and drops entries it has not read recently when full ([Vercel runtime cache](https://vercel.com/docs/runtime-cache), checked 10 Nov 2026); the local demo (D5's fallback) has none, so a rehearsal with the network off would show nothing. A file in the repository works offline, is reviewed in a pull request and is checked by the verifier in CI.

Note for the team (FE-26): `/session` sets `dynamic = "force-dynamic"` so it always shows current data. If `cacheComponents` is ever turned on in `next.config.ts`, remove that line: Prisma reads then run at request time anyway, but each must sit inside a `<Suspense>` boundary placed after the page's sign-in check (there is no root `loading.tsx`, see D16), and `await connection()` from `next/server` goes before a read that the build still prerenders ([migrating to Cache Components](https://nextjs.org/docs/app/guides/migrating-to-cache-components), checked 8 Nov).

## Testing

Three layers, each owner testing their own slice (8 November design review, decision 4):

1. **Unit:** pure logic (the coach, progression, schemas) with model calls replaced by saved replies; runs offline in CI.
2. **API mocking at the provider boundary:** `providers.ts` faked so timeouts, invalid JSON and rate limits are tested on purpose.
3. **Integration:** Server Actions run against a real PostgreSQL in CI, covering accounts, access tiers, billing, saving the quiz plan and logging a set. It runs in CI on every pull request (`npm run test:integration`, since #67); the coach and core-path cases are added under #79 (PR #81).

The CI pipeline is itself tested: a deliberately failing check must fail the run.

Evidence for the design choices: one note per paper in [docs/papers](papers/README.md).
