# Design review, 8 November 2026

A review of the whole stack a week before the 15 November checkpoint: how the AI coach sits in the server code, the schema, the user interface, testing, product scope, and what the literature says. Evidence for each point is in [docs/papers](../papers/README.md).

## Decisions

1. **Core features never depend on an advanced integration.** Sign-in, the quiz, the rule-based plan and logging work with no model key and no Stripe key. The external AI services sit behind one module, `src/lib/coach/providers.ts`; no route, Server Action or component calls a provider SDK directly. Coach modules pass typed data to each other (plan generation, verification, the safety note, chat), never raw model text. Pattern 1 of Ipeirotis & Rizakos (2026) and the failure analysis of Cemri et al. (2025) both point the same way: single-purpose modules, with rules enforced in code. (#76)
2. **The schema stays tight and every query has an index that justifies it.** Indexes are added only where a listed query needs one, with EXPLAIN before and after, in one migration. (#76)
3. **One design system, set up before more screens are built.** shadcn/ui on Tailwind CSS 4: Button, Input, Label and Card first, then Field with the first form that needs it. Every screen uses these components and Tailwind theme tokens; no one-off colours or spacing. (#75)
4. **Testing has three layers, and each owner tests their own slice.** Unit tests for pure logic (the coach, progression, schemas), with model calls replaced by saved replies, as now. API mocking at the provider boundary, so failure cases (timeouts, invalid JSON, rate limits) are tested on purpose. Integration tests that run Server Actions against a real PostgreSQL in CI, to catch edge cases across the stack (tier checks, saving a week, logging a set). The CI pipeline is tested on its own: a deliberately failing check must fail the run. This applies to both course projects. (#79)
5. **Scope: lifting, strength training and running only. No nutrition advice.** The coach does not give diet, calorie, supplement or meal advice; a nutrition question gets a short out-of-scope reply that points to a registered dietitian. This keeps a clear product boundary and keeps the coach away from the eating and body-image risks Bloom (Jörke et al., 2026) built guardrails for. (#43)
6. **Coach personas are a stretch, after the demo path, and change wording only.** Offering a choice of coaching style (for example technical, encouraging, or strict) adds product depth and pairs naturally with the pro tier. The persona changes how a reply is worded; the plan, the verifier, the safety notes and the guardrails are identical across personas. The default is the calm, technical style. A strict or "drill sergeant" style is opt-in only, because the evidence is against a harsh default: a high-intensity "sports coach" voice read as aggressive and stressful to users (Ipeirotis & Rizakos, 2026), and controlling instruction can undermine the autonomy and competence that predict sticking with training (Gabay & Oravițan, 2022). Which personas are free and which are pro is decided with the tier owner. (#80)

## What the literature changed

- FITTER's 98.5% safety figure is a model-judged checklist score; clinicians rated 80.6% of its plans safe. A plan verifier in code is still needed even with guideline grounding.
- He et al. (2026): the evidence that AI plans are worse than human-written plans rests on three trials, two at high or serious risk of bias. Their Box 2 case (a sedentary 58-year-old with medicated hypertension) becomes an eval profile.
- Numeric intensity targets (#65) are backed by Lee et al. (2026), not by Bloom, which deliberately avoids numeric targets.
- Gabay & Oravițan (2022): a fixed weekly schedule and enjoyment predict adherence; the planner keeps training days stable across regenerations.
